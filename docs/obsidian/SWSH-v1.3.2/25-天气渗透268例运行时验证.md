# 25 · 268 条天气渗透差异：游戏运行时验证清单

> 游戏：Sword/Shield 1.3.2；结论状态：**NOT_TESTED_ON_REAL_GAME_OR_EMULATOR**。此笔记用于安排真正的 GDB 验证，不把 pkNX 离线导出规则当成运行时事实。

## 研究结论与来源

- \`tools/pkNX/FlatBuffers/SWSH/Gen8/Wild/EncounterTableUtil.cs\` 的 \`IsPermittedWeather\` / \`IsWeatherBleedPossible\` 是第三方工具的数据筛选器。
- 在 \`tools/pkNX/pkNX.WinForms/Dumping/Gen8/GameDumperSWSH.cs\` 中，这个筛选器由 \`EncounterTable8Util.GetBytes()\` 调用，用于导出 \`encounter_sw_hidden.pkl\` 等文件，而非证明游戏本体天气分支的实现。
- 代码的 \`weather.HasFlag(permit)\` 判断的是「邻区掩码是否包含本区域整个允许天气集合」，并非「邻区掩码是否包含当前天气」。这是静态分歧的根源，但**不是证明游戏 ROM 有 Bug**。

## 真实数据与清单

\`python scripts/swsh_bleed_casebook.py --repo .\`

- \`weather_bleed_268_cases.csv\`：268 个非空有效的分歧槽位，包含版本、NSO BuildID、ZoneID、地名、区域子类型、天气、物种、形态、等级、概率权重及两种规则判定。
- \`weather_bleed_scenarios.csv\`：同版本、同 ZoneID、同天气子表的槽位归并到一次实验场景。保留代表槽位 ID 与原始槽位数量；不能把多个槽位当成多个独立游戏事件。
- \`weather_bleed_control_cases.csv\`：每个场景所在地图内，优先选权重较高、**在两种规则下都应允许**的正对照，以及 **都拒绝**的负对照（如果有）。
- \`weather_bleed_runtime_observations_TEMPLATE.csv\`：**空白**的运行时证据记录表，未填写即不代表任何实验结果。
- \`weather_bleed_casebook_summary.json\`：自动生成统计、SHA-256、两个游戏版本的 BuildID、分歧方向和实验边界。

## 如何在模拟器或实机验证

1. 分别核实 Sword、Shield 1.3.2 的 NSO BuildID 和原始 \`main\` SHA-256。避免将 NSO 文件偏移误用作 \`main+RVA\`。
2. 先从游戏内场景或静态字符串引用定位具体 \`ZoneID\`、局部天气变量与正在使用的 EncounterArchive 子表。需要 Ghidra/IDA 交叉引用及 GDB 动态断点证明。
3. 对同一场景至少记录本区域天气、邻区天气、明/暗雷模式、区域 ID、当前子表以及实际选择槽位。跨区域时需要同时记录实际采样的区域 hash 与位置，避免误把相邻地图结果归入目标地图。
4. 在同地点先使用正对照确认路径可触发，再观察分歧天气。保存分支地址和执行前后寄存器／内存快照；识别分支允许/拒绝必须有反汇编证据。
5. 仅凭「刷了几次没遇到」不能证明槽位不可出现。若拿不到游戏运行时判定分支，观测数据应标为 \`OBSERVATION_ONLY\`，不能声称已经验证所用算法。
6. 仅当 BuildID、ZoneID、天气、实际调用路径、关键分支结果、同版本指令和控制实验均齐全，才可以逐条将结果人工审核为动态已确认。

运行时录制可以使用仓库的 \`scripts/swsh_weather_gdb_capture.py\`（如果已配置 GDB 和经验证的分支 RVA），它**只记录断点寄存器和指令原始字节，不自动猜测分支结果或当前天气**。

## 环境缺失

目前 GitHub Actions 只能运行静态脚本和测试。它没有连到你的本地 Ryujinx、Switch 或 GDB 会话；本次不会在 CI 中生成假装来自实机的日志，也不会给尚未定位的天气判定函数编造 \`main+offset\`。
